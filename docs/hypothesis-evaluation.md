# Phase 2 — hypothesis tests and architecture boundary

**Evidence standard:** observed tool calls, preserved timestamps, tests and repository artifacts support **functional** claims; public product help supports **DOCUMENTED** capability claims. Neither implies access to protected prompts, model identity, private routing, worker allocation, or a distinct planner process. See [`phase2-research-plan.md`](phase2-research-plan.md) for preregistered alternatives; [`findings.md`](findings.md) F-20…F-22 for results; [`architecture-analysis.md`](architecture-analysis.md) §5 for Phase-1 observational equivalence.

**Distinctiveness vs Phase 1:** F-16 (historical mostly serial intervals) was scoped to its runs rather than discarded; EXP-10 refutes a **universal** serial rule and X1 matches N/d while still overlapping, narrowing the set of possible causes. EXP-11 adds an authored multi-tool plan, a conflicting requirement, a genuine same-chat continuation boundary, red→green repair and an independently replayed patch. EXP-11 is one engineering case and one artifact replay, **not** a second independent agent/model sample. F-22 improves a security test seam but says nothing about internal specialization. No need to alter `src/minagent`: the minimal functional decomposition remains sufficient to fit observed behavior.

**Why internal architecture remains non-identifiable:** the same externally logged sequence can be emitted by (A) one actor maintaining a textual plan, (B) multiple stage-specific workers coordinated behind one API, or (C) policy routing across tools. The interface exposes call/return artifacts, **not** private message boundaries. Exp-10 varies invocation and workload; Exp-11 varies task requirements and checkpoint availability, not an internal boundary intervention. Product-wide Agent Mode/help pages describe functional planning and a model-orchestrator policy; they do not expose which model(s)/route serviced this run. Different speed, word choice, formatting, roles or task quality are **not** reliable identity signatures.

**Falsifiable next experiment (minimum, if supported):** register and execute **two matched invocation envelopes in the same real session**, each N=4, d=1.0 s: (i) the *explicit* wrapper measured here and (ii) an actually submitted **direct** 4-call batch, if the supported API permits it. Preserve both return envelopes and all eight inside-call intervals; repeat each twice. If direct batching is unavailable, report that blocker and do **not** replace it with sequential assistant turns. This can discriminate an *interface-associated timing difference* while controlling N/d and session more tightly; even a repeatable difference does **not** reveal worker counts, model identity or internal architecture. A separate genuine **new-chat** continuity test remains PENDING and needs a real user-initiated chat, not a simulated reset.
